# Service notification

Contrat gRPC : `contracts/proto/ksp/notification/v1/notification.proto`. Événement publié : `notification.message.failed` (`contracts/events/notification/`). Événements écoutés : les 45 événements du Nettoyage v2 (`contracts/events/cleaning/`, ADR-054), les 3 de la facturation (`contracts/events/billing/`) et 5 événements des comptes entreprise d'identity (`identity.organization.created`, `.validated`, `.rejected`, `.suspended`, `.reactivated`, ADR-027) le paiement en ligne réussi (`payment.intent.succeeded`, ADR-031, recharge du portefeuille comprise) et les 2 événements du portefeuille prépayé (`wallet.prepaid.debited`, `wallet.prepaid.credited`, ADR-046). Recouvrement (ADR-060) : 16 événements `recovery.*` (tous sauf `recovery.case.stage_changed`) ; appelant direct `recovery` pour les messages au débiteur sans compte (ADR-061). Décisions : ADR-014 (codes par gRPC direct), ADR-021 (WhatsApp Cloud API de Meta), ADR-024 (e-mail par Brevo), ADR-025 (facturation des contrats d'entreprise), ADR-026 (e-mail vérifié), ADR-027 (comptes entreprise), ADR-028 (factures des entreprises), ADR-030 (suspension des organisations dans le Nettoyage), ADR-013 et ADR-022 (jetons de service).

Centre de notifications (ADR-039) : lecture des notifications de l'espace KSP, préférences de canaux et back-office (historique des envois, modèles) — voir « Centre de notifications » ci-dessous. Le cahier des charges complet du service (appareils push, édition des modèles, notification en direct) reste à écrire. Ce service couvre le **lot 1** (envoi des codes de connexion d'identity) et le **lot 2** (messages des événements du Nettoyage et des factures mensuelles, par WhatsApp, e-mail et dans l'espace KSP).

## Démarrer en local

```bash
cp .env.example .env
pnpm --filter @ksp/notification-service prisma:migrate   # crée les tables
pnpm --filter @ksp/notification-service dev
```

- gRPC : `localhost:50052` (adresse attendue par identity, `NOTIFICATION_GRPC_URL`)
- Santé : `http://localhost:3102/health/live` et `/health/ready`
- Métriques : `http://localhost:3102/metrics`

### Se connecter sans téléphone (développement)

Avec `NOTIFICATION_WHATSAPP_PROVIDER=console` (valeur par défaut hors production), aucun message ne part : le code demandé par identity est écrit dans le terminal du service :

```
[notification · développement] WhatsApp vers +229********45 — identity.otp : code=482913, expires_in_minutes=5
```

C'est **le seul endroit** où un code de connexion peut apparaître dans une sortie du service, et seulement en développement. Le garde-fou est double : la configuration refuse `console` quand `NODE_ENV=production` (le service ne démarre pas), et la fabrique des prestataires le vérifie une seconde fois. En production, le prestataire par défaut est `meta`.

## WhatsApp Cloud API (Meta)

`POST https://graph.facebook.com/<WHATSAPP_API_VERSION>/<WHATSAPP_PHONE_NUMBER_ID>/messages` avec `Authorization: Bearer <WHATSAPP_ACCESS_TOKEN>`, modèle d'authentification `WHATSAPP_OTP_TEMPLATE` (« Copier le code ») : le code est transmis dans le corps et dans le bouton. L'identifiant `wamid…` renvoyé est gardé dans `provider_message_id`.

| Réponse de Meta                                                     | Cause retenue          |
| ------------------------------------------------------------------- | ---------------------- |
| Erreur Graph 131026 (numéro sans WhatsApp) ou 131021                | `recipient_invalid`    |
| HTTP 5xx, 429, limites d'envoi, panne passagère, délai dépassé      | `provider_unavailable` |
| Autres refus (jeton expiré, modèle absent ou non approuvé, compte…) | `provider_rejected`    |

Les journaux ne contiennent ni le jeton, ni le numéro, ni le code : seulement le statut HTTP, le code d'erreur Graph et l'identifiant de trace de Meta (`fbtrace_id`). Délai maximum : `WHATSAPP_TIMEOUT_MS` (2 secondes par défaut, identity attend 3 secondes au plus).

## Messages des événements (lot 2)

Chaque événement écouté a sa file `notification.<événement>` (quorum), sa file de reprise `.retry` (10 secondes, 5 reprises) et sa file d'erreurs `.dlq`, créées par le kit. Le traitement (`NotifyEventUseCase`) :

1. ignore un événement déjà traité (inbox, table `processed_events`) ;
2. déduit de l'événement les messages à envoyer (`application/events/cleaning.rules.ts`, `billing.rules.ts`, `organization.rules.ts`, `account.rules.ts`) et lit les coordonnées des destinataires dans identity (`GetUsersByIds`, jeton de service), ainsi que l'e-mail de facturation des organisations pour leurs factures (`GetOrganizationsByIds`) ; identity indisponible → reprise par la file. **Seule une adresse e-mail vérifiée par code est retenue** (`email_verified` du compte, e-mail de facturation toujours vérifié) : sans elle, aucun e-mail ne part (devis, compte rendu, avis d'impayés, factures) et le message reste visible dans l'espace KSP ;
3. envoie un message par destinataire, avec la clé d'idempotence `<événement>:<modèle>:<destinataire>` (table `notifications`) : une nouvelle livraison n'envoie rien deux fois ;
4. marque l'événement traité et enregistre une notification par destinataire dans `in_app_notifications`, dans la même transaction.

Un destinataire introuvable (compte inconnu ou supprimé) est sauté ; un échec de tous les canaux publie `notification.message.failed` sans bloquer l'événement. Les journaux ne contiennent que l'identifiant de l'événement et des compteurs.

**Règle de choix du canal** (`eventChannelPlan`) : un seul message externe par destinataire, plus la notification dans l'espace.

| Nature du message                                | Canal                                                  |
| ------------------------------------------------ | ------------------------------------------------------ |
| Court, transactionnel (demande reçue, planning…) | WhatsApp ; e-mail en bascule si l'adresse est vérifiée |
| Document (devis, compte rendu, factures)         | E-mail si l'adresse est vérifiée ; WhatsApp sinon      |
| Important (sécurité ; impayés et suspension)     | WhatsApp **et** e-mail (deux envois, sans bascule)     |
| Destinataire sans téléphone ni e-mail            | Notification dans l'espace seulement                   |

| Événement                           | Destinataires                                                                      | Modèles                                                                                                                                                              |
| ----------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `billing.invoice.issued`            | client du contrat                                                                  | `billing.invoice_issued.customer` (document : numéro, période, montant, échéance)                                                                                    |
| `billing.invoice.overdue`           | client du contrat                                                                  | `billing.invoice_overdue.customer` (document : la facture impayée)                                                                                                   |
| `billing.invoice.paid`              | client du contrat                                                                  | `billing.invoice_paid.customer` (document : facture réglée, impayées restantes)                                                                                      |
| `payment.intent.succeeded`          | payeur                                                                             | `payment.receipt.customer` (document : reçu du paiement Mobile Money, montant, objet, date, référence ; ADR-031)                                                     |
| `wallet.prepaid.debited`            | titulaire, sinon le membre qui a payé                                              | `wallet.payment.customer` (court : paiement effectué depuis le portefeuille, montant, objet, solde restant ; ADR-046)                                                |
| `wallet.prepaid.credited`           | titulaire, sinon le membre ; aucun pour un crédit de la finance à une organisation | `wallet.credit.customer` (court : remboursement ou crédit de la finance, montant, motif, nouveau solde) ; rien pour une recharge (le reçu de paiement en tient lieu) |
| `identity.organization.created`     | équipe comptes entreprise                                                          | `identity.organization_requested.team` (raison sociale, référence)                                                                                                   |
| `identity.organization.validated`   | demandeur                                                                          | `identity.organization_validated.customer`                                                                                                                           |
| `identity.organization.rejected`    | demandeur                                                                          | `identity.organization_rejected.customer` (motif)                                                                                                                    |
| `identity.organization.suspended`   | demandeur                                                                          | `identity.organization_suspended.customer` (motif)                                                                                                                   |
| `identity.organization.reactivated` | demandeur                                                                          | `identity.organization_reactivated.customer`                                                                                                                         |

Équipe des comptes entreprise : `NOTIFICATION_ACCOUNTS_TEAM_USER_IDS` (même format), prévenue de chaque nouvelle demande ; lien du demandeur : `PORTAL_BASE_URL` + `/mon-espace/entreprise` (chemin du portail à valider). Demandeur = `createdBy` de l'événement, seul administrateur de l'organisation tant que les invitations n'existent pas ; une suspension ou une réactivation publiée avant l'ajout de ce champ n'est annoncée à personne. Lien des factures : `PORTAL_BASE_URL` + `/mon-espace/factures/<invoiceId>` (messages de la facturation).

Factures (`billing.invoice.*`) : facture d'un particulier : le compte client qui porte le contrat (`customerId`). **Facture d'une organisation** (`organizationId`, ADR-050) : ses **administrateurs actuels** (`admin_user_ids` de `GetOrganizationsByIds`, lus au moment de l'événement ; jamais le compte client, qui a pu quitter l'organisation), dans l'espace KSP et par leurs canaux ; l'**e-mail de facturation vérifié** reçoit seul l'e-mail, une fois (clé `<événement>:<modèle>:organization:<id>`), les administrateurs recevant alors WhatsApp ; sans lui, chaque administrateur à son adresse vérifiée. Organisation introuvable : personne n'est prévenu. Lien : `/mon-espace/factures/<invoiceId>?organisation=<organizationId>`, ouvert par le portail dans le contexte de l'organisation. Quand la fiche est connue, la raison sociale suit l'objet de l'e-mail (« Votre facture FAC-2026-000042 — SARL Bénin Propre ») ; modèles WhatsApp inchangés. Période écrite jusqu'au dernier jour facturé (la fin publiée par billing est exclue). La facture impayée désigne la facture et son montant ; l'avertissement et la suspension sont des messages du Nettoyage (v1 retirés, v2 au lot F). Le paiement en ligne envoie en plus le reçu `payment.receipt.customer` au payeur (même règle d'e-mail pour une facture d'organisation) ; la facture PDF viendra avec son lot.

Textes : `src/domain/messages/*.messages.ts` (français, dates à l'heure du Bénin, montants en FCFA entiers, sans division).

### Nettoyage v2 (CDC Nettoyage v2, 16.2 ; lot G, D40)

Règles : `application/events/cleaning.rules.ts` (demande, visite, devis), `cleaning-programs.rules.ts` (programmes, suspension, impayés, agents, réclamations), `cleaning-sessions.rules.ts` (séances et leur paiement) ; destinataires, liens et libellés : `cleaning.recipients.ts`. Textes : `domain/messages/cleaning-customer.messages.ts`, `cleaning-sessions.messages.ts`, `cleaning-team.messages.ts` (agents et personnel), et `cleaning.messages.ts` pour les six messages v1 réécrits sur place. Couverture vérifiée par `cleaning.rules.spec.ts` (un exemple de chacun des 45 événements dans `application/testing/cleaning-events.ts`).

Un dossier est désigné par son numéro (DN-000124), un programme par le sien (PN-000057), une séance par son rang (« séance 3 sur 12 du programme PN-000057 »), un lieu par les libellés du catalogue. Jamais d'adresse, de position, de téléphone ni de texte libre (16.3, test « ni adresse… ») ; jamais de montant aux agents (R-EX-04) ni au personnel (`cleaning.amounts.read` n'est pas garanti, 16.3).

**Destinataires.** Client : `customerId` du dossier. « Client » de l'argent et de la suspension (programme suspendu, cause ajoutée ou levée, reprise, avertissement d'impayés) : le particulier, ou les **administrateurs actuels de l'organisation** avec la copie à l'e-mail de facturation (ADR-050). Devis transmis pour accord : les administrateurs, chacun par ses canaux, sans copie (`billingEmailCopy: false`). Agents : ceux de l'événement (équipe, agents libérés ou retirés). **Personnel** (RV-62) : `ListStaffByPermission` d'identity avec la permission et la clé de commune de l'événement (superviseur de la zone ; un admin par son attribution globale) ; événement sans clé de commune : attributions globales seulement. Identity ne rend personne : repli `NOTIFICATION_CLEANING_STAFF_FALLBACK` (JSON permission → identifiants), sinon `NOTIFICATION_CLEANING_TEAM_USER_IDS`. Un même modèle ne part qu'une fois par destinataire.

**Toujours envoyés** (paiement et suspension, 16.2 ; décisions du lot G) : frais de visite payés, séance à payer, payée, solde insuffisant, reprise, demande refusée, devis retiré, paiement laissé au portefeuille, client absent à la visite ; de nature `important` (WhatsApp et e-mail) : séance en retard, programme suspendu, cause ajoutée ou levée, avertissement d'impayés. **Compte anonymisé (`identity.user.deleted`, ADR-036)** : file `notification.identity.user.deleted` (`AccountErasureConsumer`, `EraseUserNotificationsUseCase`). En une transaction avec l'inbox (consommateur `notification.identity.user.deleted` dans `processed_events`) :

- les notifications de l'espace KSP du compte (`in_app_notifications`, titre et texte avec le prénom) sont **supprimées** ;
- l'historique des envois (`notifications`, retrouvé par `recipient_user_id`, index de la migration 0005) est **détaché** : `recipient_user_id` et `provider_message_id` vidés, `target_masked` vidé, `idempotency_key` (qui contient l'identifiant du compte) remplacée par `erased:<id>` ; modèle, canaux, statut, code et cause d'échec et dates restent pour les statistiques. Le texte et les variables d'un message ne sont jamais conservés (ADR-014) : rien d'autre à effacer ;
- les événements `notification.message.failed` encore dans l'outbox perdent `recipientUserId` et leur `targetMasked` (vidé).

Un second passage du même événement n'efface rien (inbox) ; un compte sans notification marque simplement l'événement traité. Les journaux ne contiennent que les compteurs. Un événement métier traité après l'anonymisation ne recrée rien : identity ne rend plus le compte (destinataire introuvable).

**Ajouter un événement** (suspension, reprise, facture…) : ses modèles dans `domain/messages`, sa règle dans `application/events`, l'entrée dans `listened-events.ts`, le modèle WhatsApp dans `infrastructure/channels/whatsapp-templates.ts`.

## E-mail (Brevo)

`POST https://api.brevo.com/v3/smtp/email`, clé dans l'en-tête `api-key`, expéditeur `EMAIL_SENDER_NAME <EMAIL_SENDER_ADDRESS>` ; objet, texte brut et HTML échappé. L'identifiant `messageId` est gardé dans `provider_message_id`. Panne, 429 ou quota du jour épuisé (402) → `provider_unavailable` ; 400 `invalid_parameter` → `recipient_invalid` ; autres refus → `provider_rejected`. Les journaux ne contiennent ni la clé, ni l'adresse, ni le texte. Avec `NOTIFICATION_EMAIL_PROVIDER=console` (défaut hors production, refusé en production), l'e-mail est écrit dans le terminal avec l'adresse masquée.

## Centre de notifications (ADR-039)

Deux services gRPC réservés à la gateway, dans `notification.proto` :

| Service                    | Méthodes                                                                                                                                                                                                    | Accès                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `InAppNotificationService` | `ListMyNotifications` (plus récentes d'abord, `unread_only`, nombre de non lues), `CountMyUnreadNotifications`, `MarkNotificationRead`, `MarkAllNotificationsRead`, `Get`/`UpdateMyNotificationPreferences` | utilisateur du contexte, ses seules notifications                        |
| `NotificationAdminService` | `ListDeliveries` (filtres : modèle, canal essayé, statut, période en jours du Bénin, compte), `GetDelivery`, `ListMessageTemplates`                                                                         | `super_admin`, `support_agent`, double authentification de moins de 12 h |

- **Lecture** : pagination par curseur (identifiant du dernier élément) sur `(created_at, id)` décroissants ; une notification d'un autre compte est introuvable (`NOTIFICATION_NOT_FOUND`) ; marquer lue est idempotent (la première date de lecture reste). Index partiel des non lues (migration 0006).
- **Préférences** (table `notification_preferences`, une ligne par compte qui a choisi ; WhatsApp et e-mail sinon) : elles ne s'appliquent qu'aux **messages facultatifs** — messages d'événements adressés au client (`.customer`), ni importants (impayés, suspension), ni de la suppression du compte (`domain/preferences.ts`). Les codes, les messages importants et ceux des équipes (`.agent`, `.team`) partent toujours ; la notification de l'espace KSP est toujours enregistrée. Canaux écartés : compteur `optedOut` du traitement, distinct de `unreachable`.
- **Historique au back-office** : la table `notifications` ne contient jamais le texte ni les variables (ADR-014) ; le détail montre modèle, canaux essayés, canal utilisé, statut, code et cause d'échec, destinataire masqué, identifiant chez le prestataire et dates. La clé d'idempotence n'est jamais rendue (elle contient l'identifiant du compte) ; un envoi détaché d'un compte supprimé est signalé `erased`.
- **Modèles** : catalogue en lecture seule (`domain/catalog.ts`), texte rendu avec le nom des variables entre accolades (`{first_name}`) — aucune valeur réelle ; un texte qui dépend d'une valeur (motif, nombre) montre une seule variante. `identity.otp` n'a pas de texte ici (modèle WhatsApp rédigé chez Meta).
- **Suppression du compte** (ADR-036) : les préférences du compte sont supprimées avec ses notifications de l'espace.
